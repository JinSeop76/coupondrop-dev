## 한 줄 소개
**한정 수량 쿠폰을 선착순으로 발급하는 이벤트 플랫폼.** 대량 동시 요청에서도 **초과 발급 0건 · 중복 발급 0건**을 보장하는 것이 목표다. 동시성 제어 방식을 **7단계로 바꿔 가며 직접 구현하고 수치로 비교**한다.

---

## 핵심 설계 — 동시성 제어 단계별 비교 ⭐

> 이 표가 프로젝트의 핵심 결과물이다. README 첫 화면과 면접 답변의 중심이 된다.

| 단계 | 방식 | 구현 시기 | 예상 결과 (실측으로 확인할 것) |
|---|---|---|---|
| **v0** | 제어 없음 | S1 | 초과 발급 발생 — **경쟁 상태를 직접 재현** |
| **v1** | `synchronized` | S2 | 서버 1대에선 막히지만 **2대에선 실패** — 분산 환경의 한계 확인 |
| **v2** | 비관적 락 (`@Lock(PESSIMISTIC_WRITE)` → `SELECT … FOR UPDATE`) | S2 | 정합성 OK, 대기로 TPS 저하 |
| **v3** | 낙관적 락 (`@Version` + 재시도) | S2 | 충돌이 많으면 재시도 폭주 — 선착순에 불리한지 확인 |
| **v4** | Redis 분산락 (Redisson) | S5 | DB 부하 감소, 락 타임아웃·커밋 순서 이슈 |
| **v5** | Redis 원자 연산 (`INCR` 수량 카운트 + `SADD` 1인 1매) | S5 | 높은 TPS, Redis-DB 정합성 과제 |
| **v6** | Redis 선검증 + Kafka 비동기 DB 저장 | Phase 2 | 응답 속도와 DB 부하 분리, 최종 일관성 |

**공통 최종 방어선:** `issued_coupon`에 `UNIQUE(event_id, member_id)`를 둔다. 어떤 방식이 뚫려도 DB가 중복을 거부한다.
